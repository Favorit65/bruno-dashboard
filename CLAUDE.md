# Bruno Dashboard — контекст для Claude Code

Проект: аналитический дашборд + презентация по данным Bruno API (обслуживание
объектов ВТБ), практика в ВТБ. Полное обсуждение и история решений ведутся в
ДРУГОМ чате (Cowork/claude.ai, проект «Bruno») — этот файл лишь конспект для
быстрого старта локальной сессии, он НЕ синхронизируется автоматически. Если
чего-то не хватает — попросите пользователя обновить этот файл или скопировать
актуальный `ТЕХПЛАН_дашборд2.0_конвейер.md` из того чата.

## Конвейер дашборда 2.0 (согласованная архитектура)

1. `fetch_bruno.py` (корень репо) — посуточная выгрузка сырых данных из Bruno API
   в архив. ГОТОВ, протестирован, бэкфилл выполнен.
2. Архив — ветка `data-archive` (orphan, без истории кода main), структура
   `raw/YYYY-MM-DD/{taskPlan.jsonl.gz, statByZone/Employee/Team.json.gz}`,
   `dirs/YYYY-MM-DD/` (справочники), `manifest.json`. Бэкфилл 01.01.2026–19.08.2026
   (231 день, 1 584 993 записей taskPlan, ~212 МБ) ЗАЛИТ.
3. `build_model.py` — собирает единый агрегат `model.json.gz` из архива. ГОТОВ.
   Содержал баг группировки по датам (`dateLocal` с часом вместо дня) — НАЙДЕН И
   ИСПРАВЛЕН 20.08.2026, модель пересобрана и провалидирована.
4. `dashboard_v2.html` — self-contained HTML на `model.json.gz`, распаковка на
   клиенте, вся арифметика по фильтрам в браузере. В РАБОТЕ (поэтапно): блоки 01
   (динамика и категории) и 03 (план-факт) готовы; 02 (структура), ряд ролей/
   feedback и 04 (персонал) — следующие проходы.
5. `pptx_pipeline/*` — перевести с `report_data_v3.json` на `model.json`. НЕ НАЧАТО.
6. GitHub Actions: `build-data.yml` переписать под новый конвейер (cron + кнопка,
   коммитит `model.json.gz`), старый конвейер `data.json.gz` не трогать пока жива v3.
   Новый `build-report.yml` — кнопка → pptx → artifact + `report_latest.pptx` на Pages.

## Важные технические решения (не переоткрывать без причины)

- Источник правды по персональной/командной статистике — `statByEmployee` /
  `statByTeam` / `statByZone` (нативные агрегаты Bruno), НЕ самодельная агрегация
  через `taskPlan.employeeID` / `employees[0]` (см. находку: `statByZone` =
  `statByTeam` + `statByEmployee` сходится день в день без расхождений).
- Архив хранит SLIM-набор полей `taskPlan` (см. `SLIM_FIELDS` в `fetch_bruno.py`),
  не все 45+ полей — состав подобран по фактической заполненности полей.
- Для атрибуции роли сотрудника — фильтровать `user.projects[]` по нужному
  `projectID`, НЕ брать `projects[0]` (пользователь может состоять в нескольких
  проектах с разными ролями).
- Статусы `taskPlan.status`: 5 значений — `NEW/WAITING/COMPLETING/COMPLETED/MISSED`,
  не 3, как в старом коде `extract_aggregate_v3.py`.
- Глубина истории для 2.0 — с 01.01.2026 (не с 2025).
- Обновление данных — ежедневно по cron + кнопка (workflow_dispatch).
- `dateLocal` в записях Bruno — 10 цифр `YYYYMMDDHH` (с часом), НЕ 8 цифр
  `YYYYMMDD`. День = первые 8 цифр. Баг на эту тему уже был и исправлен в
  `build_model.py::day_of()` — не наступать повторно при написании нового кода
  по датам.

## Незакрытые вопросы к Bruno (письмо отправлено, ответов пока нет)

- URL эндпоинта чтения feedback как отдельного ресурса (нет в официальной спеке
  `api-1.json`).
- Корректный путь для `taskRequest` (сейчас `/api/v2/taskRequest` → 404).
- Официальный синтаксис фильтра «поле не пустое» (сейчас подобран эмпирически).
- Есть ли поле последнего изменения записи для инкрементальной догрузки —
  кандидат `taskPlan.timestamp` (уже сохраняется в архиве на всякий случай).

Плоская, без вложенных папок под скрипты — `extract.py`, `fetch_bruno.py`,
`build_model.py` лежат в корне рядом с HTML-файлами и `README.md`.

бага с датами), не часть штатного конвейера, можно удалить.
