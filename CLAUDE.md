# Bruno Dashboard — контекст для Claude Code

Проект: аналитический дашборд + презентация по данным Bruno API (обслуживание
объектов ВТБ), практика в ВТБ. Полное обсуждение и история решений ведутся в
ДРУГОМ чате (Cowork/claude.ai, проект «Bruno») — этот файл лишь конспект для
быстрого старта локальной сессии, он НЕ синхронизируется автоматически. Если
чего-то не хватает — попросите пользователя обновить этот файл или скопировать
актуальный `ТЕХПЛАН_дашборд2.0_конвейер.md` из того чата.

## Текущее состояние (обновлено 22.08.2026, проход 14) — обращения ≠ неплановые задачи

Найдена и исправлена ФАКТИЧЕСКАЯ ошибка дашборда: блок «Обращения по объектам»
и «Воронка обращений» показывали ВСЕ неплановые задачи (записи `taskPlan` без
`taskID`), называя их обращениями. Это разные величины. По всему архиву
(01.01–22.08.2026): плановых 1 609 229, неплановых 4 792, из них с заполненным
`feedbackID` — 2 116, а уникальных обращений (feedbackID за сутки по объекту) —
1 753. Записей, где заполнены и `taskID`, и `feedbackID`, нет ни одной, то есть
задачи по обращениям — строгое подмножество неплановых.

- `build_model.py` пишет два новых куба в `model["daily"]` (старые ключи не
  тронуты): `fbByObjectDay` («дата|объект» -> `{fb, tasks, NEW..MISSED}`) и
  `fbByObjectHour` («дата|час|объект» -> `{fb, tasks}`). `fb` — уникальные
  `feedbackID`, `tasks` — записи `taskPlan` с `feedbackID`, статусы — по задачам
  (у обращения своего статуса нет). Куб презентации `report.feedbackByObjectDay`
  не тронут, методика совпадает — числа дашборда и колоды сходятся.
- `model_v2.py`: оба куба добавлены в раскладку формата 2, `fbByObjectDay` — в
  core (блок на первом экране, куб крошечный), `fbByObjectHour` — в lazy.
  `FORMAT_VERSION` не поднимался: порядок полей существующих кубов не менялся,
  добавление кубов обратно совместимо в обе стороны.
- `dashboard_v2.html`: в блоке «Обращения по объектам» тумблер **Обращения /
  Неплановые задачи**; он же переключает воронку слева (своего тумблера у
  воронки намеренно нет, иначе на экране оказались бы два разных числа
  «обращений»). Плашек теперь четыре: обращений, задач по обращениям,
  неплановых задач, объектов — последняя следует тумблеру (объектов с
  неплановыми закономерно больше: 11 против 10 за весь архив). Роль не
  действует ни на блок, ни теперь на воронку (раньше воронка шла через
  `dayAgg`, то есть с учётом роли) — в кубе обращений ролевого разреза нет.
  Если модель собрана старой версией скрипта, режим «Обращения» выключается
  сам и подписывается «нет в модели».
- **После правки кода обязательно пересобрать модель** (Actions «Обновление
  данных (архив + модель)», можно с `skip_fetch: true`), иначе на Pages куба
  обращений не будет и тумблер останется серым.

1. `fetch_bruno.py` (корень репо) — посуточная выгрузка сырых данных из Bruno API

## Важные технические решения (не переоткрывать без причины)

- Источник правды по персональной/командной статистике — `statByEmployee` /
  `statByTeam` / `statByZone` (нативные агрегаты Bruno), НЕ самодельная агрегация
  через `taskPlan.employeeID` / `employees[0]` (см. находку: `statByZone` =
  `statByTeam` + `statByEmployee` сходится день в день без расхождений).
- Архив хранит SLIM-набор полей `taskPlan` (см. `SLIM_FIELDS` в `fetch_bruno.py`),
  не все 45+ полей — состав подобран по фактической заполненности полей.
- Для атрибуции роли сотрудника — фильтровать `user.projects[]` по нужному
  `projectID`, НЕ брать `projects[0]` (пользователь может состоять в нескольких
  проектах с разными ролями).
- Статусы `taskPlan.status`: 5 значений — `NEW/WAITING/COMPLETING/COMPLETED/MISSED`,
  не 3, как в старом коде `extract_aggregate_v3.py`.
- Глубина истории для 2.0 — с 01.01.2026 (не с 2025).
- Обновление данных — ежедневно по cron + кнопка (workflow_dispatch).
- `dateLocal` в записях Bruno — 10 цифр `YYYYMMDDHH` (с часом), НЕ 8 цифр
  `YYYYMMDD`. День = первые 8 цифр. Баг на эту тему уже был и исправлен в
  `build_model.py::day_of()` — не наступать повторно при написании нового кода
  по датам.

## Формат модели 2 (21.08.2026, проход 10)

`build_model.py` пишет три файла:

| Файл | Формат | Кто читает |
|---|---|---|
| `model.json.gz` | 1 (как раньше) | конвейер презентации, запасной вариант дашборда |
| `model.core.json.gz` | 2 | дашборд — грузит сразу, рисует блоки 01, 03, 04 |
| `model.cubes.json.gz` | 2 | дашборд — догружает фоном (зоны объекта, часовой разрез) |

Формат 2 (`model_v2.py`): вместо ключей вида `дата|UUID|роль` и повторяющихся
имён полей бакета — плоские массивы чисел с фиксированным шагом плюс словари
`days` / `roles` / `dirs.*.ids`. Данные те же: `model_v2.decode()` восстанавливает
структуру формата 1 запись в запись (проверено сверкой на срезе архива).

Правки формата — только парой: `model_v2.py` (Python) и функции `mapCubesV2` /
`bucketAt` в `dashboard_v2.html` (JS) описывают одну и ту же раскладку. При
изменении порядка полей поднимать `FORMAT_VERSION`.

Замеры в браузере доступны в консоли как `window.__perf` (скачивание,
распаковка, разбор, раскладка, первая отрисовка) — по ним и сравниваем «до/после».
